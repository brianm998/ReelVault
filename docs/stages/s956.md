# s956: Thumbnails: sharp large size, fewer ffmpeg launches, atomic writes, cleanup

Summary: Large thumbnails now come from an 800 px source frame with small/medium derived in-process, scrub frames use one ffmpeg run (2 launches per new video), files are published by atomic rename, and orphaned cache files are removed on location removal and by a bounded startup sweep.

See docs/decisions/0949-thumbnail-pipeline.md.

Decisions: soft-deleted rows (`prune_photos`) keep their thumbnails; cleanup happens on hard delete (location removal)
and via the orphan sweep. A failed scrub batch publishes nothing, cleans its temp files and is not retried (at most 2 launches per video even on failure). Concurrency is covered by `cache_tests::concurrent_readers_never_see_a_partial_file`.

Review fixes: sweep skipped on the shared default cache dir; soft-deleted rows purged after 30 days with their files; large is at most 800 px (never upscaled).
Review fixes 2: sweep now runs on the default dir via a catalog registry and on OpenCatalog; failed scrub batch falls back per frame; ProRes scrub copy is atomic.
