# s956: Thumbnails: sharp large size, fewer ffmpeg launches, atomic writes, cleanup

Summary: Large thumbnails now come from an 800 px source frame with small/medium derived in-process, scrub frames use one ffmpeg run (2 launches per new video), files are published by atomic rename, and orphaned cache files are removed on location removal and by a bounded startup sweep.

See docs/decisions/0949-thumbnail-pipeline.md.

Decisions: soft-deleted rows (`prune_photos`) keep their thumbnails; cleanup happens on hard delete (location removal)
and via the orphan sweep. A failed scrub batch publishes nothing, cleans its temp files and is not retried (at most 2 launches per video even on failure). Concurrency is covered by `cache_tests::concurrent_readers_never_see_a_partial_file`.

Review fixes: sweep skipped on the shared default cache dir; large is at most 800 px (never upscaled).
Review fixes 2: sweep now runs on the default dir via a catalog registry and on OpenCatalog; ProRes scrub copy is atomic.

Review fixes 3: removed the 30-day row purge (user data); sweep always registry-keyed; exact prefix match instead of LIKE; registry written with O_APPEND.

Review fixes 4: per-video thumbnail version marker regenerates old blurry stills lazily; sweep WARNs when skipped; documented accepted limits (see 0949).

Review fixes 5: the scrub batch is all-or-nothing (at most 2 launches per video, failure included); a failed scrub batch or still regeneration records a per-video failure marker (24 h or until the source's size/mtime changes) so later requests do not relaunch ffmpeg; `shared_known_ids` no longer rewrites `.catalogs`.

Review fixes 6: merged develop (its byte-range prefix match replaces my substr change); removed per-frame scrub salvage; exit-0-with-missing-outputs is a failure; backoff by cause (none/10 min/24 h) with reason in the marker; color probed once per indexed video.
